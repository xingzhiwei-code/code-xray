# Loop Engineering 开发协议

本文将 Loop Engineering 定义为项目可执行的工作协议：以目标、真实状态、反馈、证据和停止条件组织开发。它是本项目的强制设计选择，不声称存在唯一行业标准。

## 1. 一个 Loop 的边界

一轮只推进一个可观察、可验收的用户行为或必要支撑能力。优先实现从输入到输出的纵向路径，之后逐步加深分析。不要先创建四套客户端，也不要先把所有抽象层搭满。

顺序固定：

```text
Goal → Inspect → Plan → Implement → Verify → Check
  ↑                                          ↓
Next ← Update State ← Reflect ← Evidence ← Result
```

任务记录在 BACKLOG，Loop 历史记录在 LOOP_LOG；二者不同：一个任务可以经过多轮，一轮的成功不能自动代表整个阶段完成。

## 2. 各步的输入与退出条件

| 步骤 | 必须做什么 | 退出条件 |
|---|---|---|
| Goal | 选择依赖已完成的任务，明确用户价值、AC、非目标 | 能写出输入、预期输出和反例 |
| Inspect | 读取相关规范、代码、真实工作树和已有证据 | 已知起始快照，未知项单独列出 |
| Plan | 选择最小变更面、验证方法、回退方式 | 在改代码前固定验收 oracle；不要求长计划 |
| Implement | 完成最小可用路径，维护依赖方向与隐私约束 | 有可检查的产物；任务仍未完成 |
| Verify | 运行适合风险的检查，保存命令、环境、结果 | 输出与预期逐项比较，失败/未运行明确记录 |
| Check | 换检查视角，审查需求、反例、证据及 UX | 有独立检查记录或明确的检查能力限制 |
| Evidence | 建立证据与 AC、任务、快照的映射 | 无虚构通过、无未落盘的必要证据 |
| Reflect | 总结最重要的偏差，必要时修正方案/Decision | 明确继续、返工、阻塞或完成 |
| Update State | 更新历史、任务、HANDOFF 与 CURRENT | 一致 checkpoint 可被新上下文恢复 |

## 3. Maker / Checker

Maker 负责实现；Checker 从验收条件、输入输出和代码事实重新检查，不只复述 Maker 的总结。可用独立 Agent、独立上下文或人工 reviewer，身份与能力限制必须记录。Checker 的最小输入是任务 AC、变更快照、diff、测试与证据，不需要整段聊天。

单 Agent 环境必须先封存实现和验证结果，再进入单独 check 阶段，从反例和验收重新审查。记录 `review_mode: self-separated`，不得冒称独立审查；离线基线、隐私外发控制、协议兼容、学习状态持久化等高影响改动，在发布前仍需 `independent` 检查。日常实现可先进入 review 并继续其他任务，不能假装发布闸门已满足。

Checker 必答：

- 当前行为是否满足指定 AC？哪些只在 fixture 上成立？
- 所有结论有无来源？静态事实、条件性风险和未知是否混淆？
- 有没有负例推翻规则？有没有不支持的语法被当成成功分析？
- CLI 是否清楚表达 partial/error/无变更，是否能离线和非交互使用？
- 有没有复制领域逻辑到 Surface、泄露源码或未经同意外发？
- 证据是否来自当前相关输入，是否可复现？

## 4. 验证策略

先按用户可见 Interface 验证。纯领域转换验证稳定结果；Adapter 验证真实协议或受控 fixture；CLI 验证实际入口、退出码与输出；学习状态验证保存后重新加载；LLM 验证结构化结果校验、虚构引用拒绝和故障回退。

规则案例必须同时包含：命中条件、允许条件、禁止误报、未知/不支持输入、预期 Evidence。对风险规则不要只写“能发现问题”的正例。期望结果应在实现前确定，不能从本次输出反推期望值。

对已有 bug，先得到可重复失败或足够定位证据，再修复并回归。对低影响可逆文档/样式修改可用链接检查或人工核对，不为凑覆盖率写镜像测试。对数据、协议和隐私相关改动必须有对应行为验证。必需检查通过后，仅在新增变更或未解决风险时扩展检查。

LLM 文案允许变化，但证据引用、事实支持、schema、隐私与 baseline 结果必须稳定可测；用固定输入/固定 provider stub 检查契约，并将真实 provider 检查作为独立、按授权运行的外部集成证据。

## 5. 不同级别的完成

- `实现已写`：存在产物，不是 Done。
- `验证通过`：指定检查在记录的快照通过，不代表所有场景可靠。
- `任务 done`：AC 全部满足、必要证据与 review 完成、状态已保存。
- `阶段可发布`：本阶段必需任务全部 done，PRD 阶段闸门满足，且发布操作具备授权。

缺少依赖、无法运行、跳过、取消、超时均不得记作 passed。范围相关输入变化会令相应证据失效；只补跑受影响检查，不机械地重跑全部。

## 6. 失败与停止

失败时追加一条结果和原因假设，不覆盖旧失败。连续两次使用同一假设没有新证据，下一轮必须改变诊断路径、缩小输入或寻求复核；不得把次数限制当作“完成”。阻塞记录具体外部条件，独立任务仍可推进。

需要压缩上下文、换模型、结束会话、切换分支或遇到权限阻塞时，先 checkpoint。任务尚未完成就明确写未完成，并留下第一条可执行动作，不能留下“继续完善”作为下一步。

## 7. 一轮最小记录

最少含：Loop ID、Task ID、session、目标/AC、起始快照、变更范围、验证 Evidence ID、check 方式、结果、失败或未知、下一步、checkpoint revision。完整字段见 [RECORD_TEMPLATES.md](RECORD_TEMPLATES.md)。

完成判定与记录格式由版本控制保存，不依赖特定模型、IDE 插件、记忆系统、聊天工具或付费编排服务。
