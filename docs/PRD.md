## 版本规划总览：一共四个产品版本

已经规划 **v0.1 CLI → v0.2 VS Code Extension → v0.3 JetBrains Plugin → v0.4 AI Coding Agent Integration**。四个版本逐步交付、分别验收，共享同一个 Engine；后续版本继承已完成能力，并增加新入口或分析深度。

| 产品版本 | 主要解决的问题 | 这一版具体交付 |
|---|---|---|
| **v0.1 CLI：先把分析做出价值** | AI 写完后端后，我能看懂改了什么、哪里需要检查吗？ | cliff CLI、Java/Spring/JPA 确定性分析、变更摘要、静态路径、风险证据、上下文解释、学习记录、认知债务、可选 LLM 增强 |
| **v0.2 VS Code：融入日常编码** | 我能在写代码和看 diff 时直接理解，而不反复切终端吗？ | VS Code 扩展、侧栏报告、行内提示、Hover/CodeLens 入口、选中代码解释、变更审查、学习与债务面板 |
| **v0.3 JetBrains：深入 Java 工程场景** | 我能在 Java 常用 IDE 中看清 Bean、代理、事务和持久化关系吗？ | JetBrains 插件、IDE 导航/后台分析、经验证的 PSI 事实补充，以及 Bean/事务/JPA 三类有边界的分析深化 |
| **v0.4 Agent Integration：接入 AI 开发闭环** | AI 每轮改完代码，能自动给出有证据的审查并留给我判断吗？ | 统一工具接口、修改后扫描、前后对比、结构化审查结论、待验证/待学习清单、至少两个不同 Agent 宿主接入 |

完整的逐版本功能、用户流程、交付物和验收见**第 8 节**。第 2—7 节和 AC01—AC12 详细规定 v0.1，不能据此认为项目只有一个版本。文档版本 1.1 是本 PRD 的修订号，不是新增的产品版本。

## 1. 定义与目标用户

Code X-Ray 是面向 AI Coding 的代码理解与维护判断工具。它把代码事实、可能风险、隐含机制、上下文学习和个人认知债务连接起来，让开发者知道下一步该检查什么、学习什么。

| 用户 | 场景 | 需要完成的工作（JTBD） |
| --- | --- | --- |
| 首要：从前端转向 Java 全栈、经常依赖 AI 写后端的开发者 | AI 刚生成一个 Spring Boot 功能，接口能返回，但不确定事务和持久化行为 | 从自己的代码定位高价值检查点，理解机制，知道怎样验证 |
| 次要：进入陌生框架的成熟开发者 | 接手既有服务或评审陌生改动 | 快速了解可见路径、变化影响与分析盲区，避免把静态猜测当运行事实 |
| 后续：大量使用 Coding Agent 的开发者 | Agent 反复修改代码，人的理解未同步 | 使用统一结构化结果设置检查与学习入口，并持续保留个人理解状态 |

核心用户结果：一次扫描后能找到有证据的检查点；从检查点理解当前代码机制；以小验证检验理解；代码变化后知道哪些理解需要复核。

## 2. v0.1 唯一必须跑通的纵向闭环

场景：用户打开一个本地 Java / Spring Boot / JPA 示例项目，在不配置模型、不上传代码的情况下完成：

1. 执行 `xray`（等价于 `xray scan .`），看到覆盖摘要、最多 3 个优先展示的发现和下一步。
2. 选择一个发现，查看源码位置、确定性事实、推断前提及静态可见路径。
3. 查看贴合此处代码的四段学习卡与一个短验证问题。
4. 将个人学习状态保存为学习中、自述理解或经验证理解，查看透明的债务变化。
5. 修改示例代码，再扫描或与显式 Git 基线对比，看到事实变化、失效证据与需要复核的学习关联。
6. 导出同一报告的 JSON；退出后再次打开，可恢复本项目学习状态。

此闭环必须有正例、反例、未知和失败样例。不能用手工编写固定报告代替真实代码分析。

## 3. 首版范围与明确不做

| 领域 | v0.1 必须交付 | 首版边界 |
| --- | --- | --- |
| 输入 | 本地源码目录；识别 Maven 或 Gradle 项目标志；记录文件覆盖与跳过原因 | 先支持一个模块；多模块只分析明确选中的模块并提示范围；不执行构建 |
| Java | 解析包、类、方法、注解、可见调用和常见 JPA 元信息，输出源码证据 | 支持的 Java 语法和框架版本经技术 spike 固定；不能把所有版本写成支持 |
| 规则 | 至少 3 个有明确前提、反例、未知状态的 Spring / JPA 规则；规则清单公开 | 只报告可被现有解析能力支持的风险信号；无全程序精确分析承诺 |
| 路径 | 从已识别入口到本地可解析服务/持久化调用的静态路径 | 外部依赖、反射、代理与动态分派可终止为 unknown；不宣称实际执行顺序 |
| Diff | 与用户明确提供且可解析的 Git ref 对比，展示变化文件/符号与已知关联影响 | 未提供基线不猜测 main；非 Git 项目说明不可用，其他功能仍可用 |
| 学习 | 内置的版本化确定性学习模板、代码位置绑定、短验证和本地状态 | 不做完整课程平台；LLM 可增强措辞，不能成为必要依赖 |
| 债务 | 概念 × 代码关联、透明启发式因子、未知项、用户更正/忽略/删除 | 不做个人排行榜、能力评级、跨团队比较或绩效集成 |
| CLI | cliff 驱动的可安装 CLI；TTY 与 JSON/非交互输出；doctor 自检 | 不做默认全屏 TUI、账号、云端后台 |
| 持久化 | 本地报告/缓存与个人学习记录隔离，记录 schema 版本，提供清除操作 | 个人数据默认不入 Git；不做云同步 |

三类首版规则候选为：同类内部调用事务注解方法时的代理边界检查点、持久化调用位于循环时的查询放大检查点、Web 出口暴露实体/关系时的加载或序列化检查点。它们是产品候选，需在技术 spike 后根据可靠的语义解析能力定稿；定稿须有官方机制依据、正反 fixture 与未知边界。若替换候选，需要 Decision 说明，并继续满足三类有限规则的要求。禁止把这些静态形态直接命名为“已确认事务失效”“已发生 N+1”或“已发生泄露”。

首版不做：自动编辑用户业务代码、自动修复/合并、生产运行采集、全仓库知识图谱平台、多语言并行建设、IDE 插件实现、强制 LLM、完全漏洞检测、商业账号与计费。未来形态可提前设计协议，不能抢占 v0.1 闭环验证。

## 4. 用户交互与命令契约

以下是产品行为契约；参数拼写在冻结前可通过 Decision 调整，四个 Surface 的业务语义保持一致。默认可见信息尽量少，能力通过按需展开提供。

| 命令 | 用户得到什么 | 关键行为 |
| --- | --- | --- |
| `xray` | 当前目录的默认摘要与下一步 | 无参数等价于 `xray scan .`；无需理解命令列表即可开始 |
| `xray scan [path]` | 本次覆盖、优先发现、下一步、报告 ID | 缺省 path 为当前目录；不要求 API key；无 TTY 不询问 |
| `xray explain <finding-id>` | 源码证据、适用前提、静态路径和四段学习卡 | 只从对应报告/快照解释；源码已变时提示陈旧并提供重扫动作 |
| `xray diff --base <ref>` | 显式基线到当前工作区的变化与已知影响 | 包含未提交改动；说明对未跟踪文件的策略；ref 失败不静默换基线 |
| `xray learn <finding-id 或 concept-id>` | 一次短学习与检验、个人状态 | 可跳过；非交互状态修改必须使用显式参数；不自动判定掌握 |
| `xray debt` | 待处理概念、代码关联、因子、未知项与版本 | 支持查看细项、修正、忽略、删除；概览不出现伪精确能力分数 |
| `xray doctor` | 环境/依赖/支持范围/本地数据目录诊断 | 不泄露环境变量值或秘密；无网络也能完成本地检查 |

共同要求：`--help` 提供最短可用示例；`--format json` 输出版本化纯 JSON，诊断写 stderr；`--offline` 强制禁用远端增强；`--no-color` 与 `NO_COLOR` 均被尊重。清理缓存、删除个人状态与 LLM 配置的具体子命令在 CLI 契约冻结时明确，不能只存在底层 API。

首屏采用“结论 → 依据 → 下一步”的顺序。默认最多展示 3 项，显示剩余数量和展开方式；单项包含严重度、结论类型、简短原因与源码路径。覆盖不完整的提示必须可见，不能藏在详情中。

错误必须给出发生了什么、哪些结果仍可用、一个可执行下一步。取消应及时停止后续工作，写出已完成结果的真实状态并避免留下貌似成功的半份报告。

### 必须设计和验证的状态

| 状态 | 预期体验 |
| --- | --- |
| 首次/空目录/无支持文件 | 清晰说明支持范围与下一步；不输出“项目安全” |
| 正常完成但零发现 | 显示规则范围与覆盖；不把未命中解释为不存在问题 |
| 部分文件解析失败 | `partial`、失败文件计数与原因；可用结果仍可查看，JSON 同样保留状态 |
| 全部解析失败/无效参数/权限不足 | 非成功状态；错误定位与修复建议；不伪造空的成功报告 |
| 未解析外部符号/动态机制 | 路径终点与规则前提显示 `unknown`；不连接猜测的调用边 |
| 离线/模型未配置/超时/额度或响应错误 | 基础报告和模板学习可用；增强项标明未生成，可重试 |
| 非 TTY/管道/CI | 无动画、无询问、无 ANSI；JSON 可解析且不混入提示文案 |
| `NO_COLOR`/窄终端/中文长路径 | 不仅靠颜色表达；60 列仍能换行读取；路径可展开查看完整值 |
| 中断/损坏状态/旧 schema | 不覆盖可恢复数据；说明恢复办法；迁移或显式错误不得静默丢记录 |
| 报告后源码变化/ID 不存在 | 提示快照已变化或找不到对象；不能把旧行号当作新源码证据 |

退出码、报告状态和发现严重度必须分别定义：发现风险可以是一次成功分析；`partial` 与执行失败不得与完整成功混淆。具体码值由 [架构](ARCHITECTURE.md) 的唯一协议定义。

## 5. 结果与证据要求

每次报告至少包含：报告 ID、输入快照、Engine/分析器/规则版本、时间、支持范围、成功/跳过/失败文件统计、未解析项、发现和证据引用。每个 finding 至少包含稳定标识、规则 ID、结论类别、严重度、依据、前提、不确定性、代码位置和可行验证方法。

结论类别为 `fact`、`inference`、`recommendation`、`unknown`；人工/运行验证可增加验证状态，不能通过高置信度自动把推断变成事实。证据内容与源码快照绑定；哈希变化后显示 stale，只有重新分析或明确重新验证才能更新适用性。

排序依据需可解释。发现很多时按维护影响、证据质量与当前改动相关性排序；用户可看到排序理由。学习状态可以影响个人建议顺序，但不能隐藏仍存在的代码发现。

## 6. Contextual Learning 与认知债务

一张学习卡必须回答四个问题，并引用当前 finding / concept / evidence：

1. **What**：这里使用了什么机制，用当前代码解释。
2. **Why here**：可从代码支持的作用是什么；作者意图未知时明确标为推断。
3. **Hidden mechanisms**：相关代理、事务边界、持久化上下文、加载或查询行为的适用前提。
4. **What if changed / removed**：条件化说明可能变化，并给出可验证步骤；不编造运行结果。

每卡提供一个短问题或预测题，以及答案依据。确定性题可依据明确规则评分；开放解释只记录用户自述或待人工验证，LLM 评价不能独立升级为已验证理解。验证记录保存概念版本、题目/检查方式、结果、证据和时间；默认不保存含源码或秘密的自由回答。

学习状态采用：`未评估 → 待学习 → 学习中 → 自述理解 → 已验证理解`；`待复核`和`忽略`是独立状态。转换必须有事件来源。浏览只记录浏览，不能触发掌握；重扫也不能抹掉历史。源代码或概念解释版本变化时标记关联待复核，提示原因，保留原验证。

债务 v0.1 可采用下述透明启发式作为起点，最终版本须写入 Decision 和输出。对于已评估的“概念 × 代码关联”项：

`priority = impact × gap × evidenceStrength`，三个因子均为 `[0, 1]` 的有限映射。

- `impact`：已知维护影响档位，例如低 0.3、中 0.6、高 1.0；必须显示档位来源，不能暗示事故概率。
- `gap`：待学习 1.0、学习中 0.7、自述理解 0.4、已验证理解 0.1；这些是排序策略，不能解释为真实理解百分比。
- `evidenceStrength`：直接可解析关联 1.0、有限推断 0.5；未知关联不计算，列入“待确认”。
- `未评估`与`待复核`不强行赋分，分别显示计数和待办；忽略项保留理由且不计入当前个人建议。

示意：中影响 0.6 × 学习中 0.7 × 直接关联 1.0 = 0.42，只表示本版本内的建议优先度。它不是 42% 不懂、42% 风险或能力分数。默认展示优先级和因素；合计必须同时展示计算项数量、未知数量、覆盖范围、去重规则与 `debt-model-v1`。同一证据重复命中不得重复累加；不同模型版本的汇总不能直接比较趋势。

用户必须能够纠正概念关联、设置自述状态、补充验证、忽略/恢复和删除。删除个人状态不等于删除客观 finding；修复代码也不自动证明用户掌握机制。数据属于个人，不提供团队排名或管理者绩效视图。

## 7. 隐私、确定性与可选增强

默认扫描无网络、无遥测、无账号、无模型密钥；确定性主链路不执行目标项目代码。LLM 只能在已产生事实和证据之后补充解释、问题建议或自然语言导航。提供方可替换，选择与密钥属于本机配置，不能硬编码某一模型名称为业务前提。

远端增强需用户明确启用，说明将发送的最小片段和目的，并保留本地禁用能力；日志、缓存和导出不得包含密钥。被分析内容包含提示词时只作为源码数据。提供方失败或产生无证据结论时丢弃/标记增强结果，原确定性报告保持可用。

个人状态、分析缓存、LLM 缓存和可分享报告有分开的保留与删除策略。默认分享报告只含必要相对路径和脱敏摘要，源码片段与个人状态需显式选择。所有持久化格式有 schema 版本；损坏时不能静默重置。

## 8. 四个产品版本：功能、流程与完成标准

### 8.1 共同继承规则

- 顺序是 v0.1 → v0.2 → v0.3 → v0.4；每版能独立安装、演示和验证。发布下一版时保留已有 CLI 的可用性与契约兼容。
- 风险、路径、解释、学习状态和债务规则由同一 Engine 维护；Surface 只适配输入、宿主能力与呈现。不能按客户端各做一套业务逻辑。
- 每一版都必须保持离线基线、证据可追溯、隐私默认、渐进展开和简单 UI。新入口不能让已有用户重新配置同一份个人学习档案。
- 产品内的学习记录从 v0.1 起存在；**开发本产品的 Markdown 进度与跨模型接力从第一天强制执行**，不等到 v0.4 才做。
- 第 8 节定义四版的范围基线。进入后续版本时把其验收拆成子任务、固定支持矩阵；如需修改范围，记录 Decision，不再从空白重新规划。

### 8.2 v0.1 — CLI：验证分析本身有价值

**核心问题**：一次真实 Java 后端改动，能否转化成开发者看得懂、能检查、能继续学习的结果？

**必须交付的能力**：

1. 基于 cliff 的 `xray` 默认入口，及 scan / diff / explain / learn / debt / doctor；包括结构化输出、非交互模式与数据清理。
2. Java / Spring Boot / JPA 源码结构、有限框架事实、至少三类有正反例的规则；显示分析范围和 unknown。
3. 显式 Git 基线的变化文件/符号与已知影响摘要、入口到本地服务/持久化调用的静态可见路径。
4. 有源码快照依据的风险、四段上下文解释、短验证题、本地学习状态与可解释的认知债务。
5. 可选 LLM 解释增强；断网、没有密钥或模型失败时核心用户流程仍完整可用。

**用户流程**：AI 修改订单功能 → 执行 `xray` 或 `xray diff --base <ref>` → 阅读优先检查点 → 跳到证据 → 理解事务/JPA 机制 → 保存学习状态 → 修改后重扫。

**交付物**：可安装 CLI、共享 Engine/Protocol、Java Adapter、示例项目、规则评估集、安装与隐私说明、开发状态记录。

**本版不做**：VS Code/JetBrains 插件实现、Agent 自动触发接入、多语言深度实现、云平台、自动修改业务代码。

**完成标准**：AC01—AC12 全部通过，T001—T010 完成；不能用命令壳或固定示意报告代替真实分析闭环。

### 8.3 v0.2 — VS Code Extension：在编码现场理解

**核心问题**：开发者能否在熟悉的编辑器中高频查看结果，而不反复切换终端和复制路径？

**继承**：复用 v0.1 的 Engine、Java 分析、规则、报告、学习状态与债务模型。

**必须新增的能力**：

1. 扩展安装与环境自检；工作区、当前文件和当前变更的分析入口。默认手动触发，可选择启用有节流与取消机制的保存后分析。
2. 侧栏显示变化、风险、静态路径、知识点和债务摘要；默认只呈现重点，点击后再展开来源和机制。
3. 在适用位置提供 Hover / CodeLens / 轻量行内标记；显示摘要或“解释此处”入口，避免同一行重复堆叠提示。
4. 选中代码或符号后解释 What / Why here / Hidden mechanisms / What if removed；显示适用快照与未知项。
5. Diff 审查中呈现新增、持续、移除和无法比较的发现，支持一键跳转原始或当前证据；明确选择基线。
6. 学习卡、短验证、学习状态与债务详情可以在侧栏操作；与 CLI 使用同一工作区身份和数据版本，跨入口写入幂等。
7. 编辑缓冲区有未保存改动时标明“尚未分析”，或在已声明支持的缓冲区快照上重新分析；不能把磁盘旧行号套到新内容。覆盖安装、升级、禁用、卸载、错误与取消体验。

**用户流程**：编辑订单服务 → 点击“分析当前变更” → 侧栏看到事务检查点 → 行内查看证据/解释 → 做一个短验证并保存 → 修改后刷新发现。

**交付物**：可安装 VS Code 扩展、命令/侧栏/行内交互、宿主适配层、安装升级说明、真实扩展宿主验证记录。

**本版不做**：复制 Java 规则、默认开启全工作区频繁扫描、自动修复/合并、JetBrains 实现或 Agent 自动审查工作流。

|---|---|

| V02-2 | 相同输入快照、配置、分析能力与版本下，CLI 和扩展的规范化领域结果一致；UI 没有独立规则或债务公式 |

### 8.4 v0.3 — JetBrains Plugin：深化 Java / Spring / JPA 理解

**核心问题**：在 Java 常用 IDE 中，能否把框架隐含机制与实际源码关系讲得更具体、更有依据？

**继承**：复用已有 Engine、Protocol、规则、学习/债务模型与离线能力；提供与已有入口对应的扫描、解释、证据和学习操作。

**必须新增的能力**：

1. JetBrains 插件的项目/当前文件/当前变更入口、工具窗口、代码位置菜单、提示与导航；分析在后台运行，可取消，不阻塞编辑。
2. 使用宿主可提供的 PSI/索引事实补充符号定位与引用解析；IDE 未索引完成、能力不可用或版本不支持时明确降级，不伪造已解析关系。
3. **Bean 与代理关系**：在受支持的构造器注入、Bean 定义与限定条件下定位候选来源；多实现、条件 Bean 与动态代理保留歧义，解释为何无法唯一确定。
4. **事务边界与调用上下文**：加深对事务注解、同类调用、传播配置及异常回滚条件的解释；每条提示写明适用前提，不能仅凭注解证明运行时事务生效。
5. **JPA 持久化上下文与加载**：结合实体关系、持久化调用和 Web 出口，解释生命周期、加载/序列化边界与查询放大检查点；实际 SQL 次数仍需运行证据。
6. 三类深化能力的判定与解释进入共享 Engine/框架规则 Module；JetBrains 只提供可追溯事实。其他 Surface 在相同能力可用时复用规则，不在插件中分叉。

**用户流程**：在 IDE 选中 `createOrder` → 查看 Bean/服务/Repository 关系 → 检查代理和事务前提 → 展开 JPA 机制及源码 → 保存学习记录 → 修改后重新分析。

**交付物**：可安装 JetBrains 插件、已验证的事实 Adapter、三类深化能力、IDE 与 JDK/框架支持矩阵、规则正反例与真实宿主测试证据。首发 IDE 产品与版本在进入本阶段时核实固定，不宣称覆盖整个 JetBrains 产品线。

**本版不做**：全量 Spring 容器模拟、生产动态追踪、精确预测所有 SQL、全框架支持、借 IDE 能力取消证据和 unknown 约束。

**验收与任务**：T201 拆分实施，以下 V03 条件全部满足后方可完成：

| 编号 | 可观察的完成条件 |
|---|---|
| V03-1 | 在声明支持的真实 IDE 中完成分析→导航→机制解释→学习保存；插件安装/升级/卸载、索引中/错误/取消行为有证据 |
| V03-2 | Bean、事务、JPA 三类深化能力各有公开的支持边界与正例/反例/未知案例；每类至少 2/2/1 个，分别记录命中、误报与未解析原因 |
| V03-3 | 同快照、配置、版本与能力集合的通用结果与 CLI/VS Code 一致；额外 PSI 事实注明来源、能力与快照，不把输入能力不同造成的差异藏起来 |
| V03-4 | 跨进程协议、IDE 坐标转换、索引失效、后台任务与取消验证通过；业务规则留在共享 Engine，现有 CLI/VS Code 通过受影响回归 |

### 8.5 v0.4 — AI Coding Agent Integration：进入生成后的审查闭环

**核心问题**：AI 每轮修改后，能否自动得到可追溯的变化、风险和学习清单，让开发者据此决定下一步？

**继承**：已有分析 Engine、统一证据、Java 深度、解释、个人学习/债务与各 Surface；不绑定单个模型供应商。

**必须新增的能力**：

1. 统一的能力发现、分析、差异对比、解释和证据读取工具接口；宿主桥接可以采用已验证的本地 stdio/工具协议，公共领域模型保持不变。
2. 至少两个不同 Agent 宿主的实际接入示例。目标包括 Codex、Claude Code 等可选宿主，支持方式与版本需在实施时实测，不把本规划当成现成集成能力。
3. 用户显式启用后，在 Agent 一轮修改结束时触发本地分析，或以明确的命令/流程节点调用；记录改动前基线与改动后完整快照，包括选定的未提交内容。
4. 输出结构化审查：变化摘要、静态路径影响、新增/持续/移除风险、源码证据、未知覆盖、建议验证、相关概念与债务变化。模型切换不改变同一快照的确定性结论。
5. 提供可配置的审查关口：区分“分析完成”“需要人工检查”“分析不完整/失败”，同时返回原因和证据。默认给出审查结果；只有用户明确配置宿主策略后，才能让发现影响流程是否继续。
6. 开发者能从 Agent 结果跳到 CLI/IDE 报告，理解后再决定接受、修改或补验证；Agent 不替用户确认知识掌握。
7. 为同一次审查记录稳定 ID、基线/目标快照、工具与规则版本，换模型后可重新读取；重复触发幂等，旧快照结论不能冒充新改动结果。

**用户流程**：用户给需求 → Agent 改代码 → 已启用的 X-Ray 步骤审查变更 → 返回风险/证据/未知与学习清单 → 用户检查或要求修改 → 重扫同一工作流的新快照。

**交付物**：统一工具契约、至少两个宿主的 Adapter/接入说明、修改后审查流程、结构化结果与状态规范、跨宿主演示和失败/取消/注入测试。

**本版不做**：自建代码生成模型、重新实现 Coding Agent、默认执行用户项目的构建/测试、自动批准或合并代码、仅凭启发式 finding 宣称可以安全上线。

**验收与任务**：T301 拆分实施，以下 V04 条件全部满足后方可完成：

| 编号 | 可观察的完成条件 |
|---|---|
| V04-1 | 两个不同宿主都实测完成“修改→分析→读取证据→再修改→重扫”；相同输入与能力的确定性结果一致，差异只来自允许变化的表达/宿主行为 |
| V04-2 | 初次启用、自动触发、重复请求、取消、超时、工具错误与不完整覆盖有契约测试；partial/failed/unknown 不被包装成审查通过 |
| V04-3 | 报告标识、基线和目标快照可核对；代码变更后旧审查明确过期；换宿主可根据持久记录重新获取报告，不依赖私有聊天记忆 |
| V04-4 | 默认本地与权限约束有效；恶意源码不变成工具指令；可配置的流程关口只在用户启用范围内生效；现有三个 Surface 的相关回归通过 |

### 8.6 阶段进度与后续扩展

当前四个版本均未实现，执行从 v0.1 的 T001 开始。Backlog 中 T101/T201/T301 是后续版本入口任务，进入阶段时按本节明确范围拆分，不提前把它们标为 ready 或 done。AC01—AC12 仅用于 v0.1；V02/V03/V04 是对应后续版本的验收组，不是 v0.1 前置条件。

四版完成后，预期形成“一个共享 Engine + CLI/VS Code/JetBrains/Agent 四个入口”的产品闭环。完成每版需提交自己的功能证据；“能换模型继续开发本产品”与“产品已经接入某 Agent”是两件不同的验收事项。
